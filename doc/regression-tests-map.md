# Regression suite map: test → BEEP functionality covered

This document maps every test in the LibVortex regression suite
(`test/vortex-regression-client.c` + `test/vortex-regression-listener.c`) to the
functionality it exercises.

It has two audiences:

- **LibVortex maintainers** — to know what a given `test_NN` actually protects before
  changing code near it, and to spot uncovered areas.
- **Authors of other BEEP implementations** — this suite is the conformance oracle used to
  validate and certify new implementations of the protocol. Because the client and the
  listener are two separate processes talking BEEP over a socket, they can be crossed: run
  the C `vortex-regression-client` against a foreign listener, or a foreign client against
  the C `vortex-regression-listener`. Sections *Listener contract* and *Profiles* below
  describe what the listener side must provide for that to work.

Generated by reading the sources; the authority is always the code itself
(`test/vortex-regression-client.c`).

## Running the suite

Two terminals, from `test/`:

```sh
./vortex-regression-listener        # terminal 1
./vortex-regression-client          # terminal 2
```

Options are consumed **positionally and only as the first argument**, so exactly one of
them can be given per run:

| Option | Effect |
|---|---|
| `--offset-port=NUM` | add `NUM` to every port the suite binds, so several runs can share a host. Accepted by **both** programs and they must be given the same value. Must come first when combined with another option |
| `--run-test=NAME` | run only the given test; accepts a **comma-separated list** (`--run-test=test_02a,test_02b`) |
| `--disable-time-checks` | skip tests that can fail because of timing; use under valgrind |
| `--skip-http-connect` | no local HTTP proxy available (test 16 family) |
| `--enable-server-log` / `--disable-server-log` | toggle logging on the *listener* and exit |
| `--enable-websocket-debug` | noPoll debug output |

Trailing positional arguments: `[listener-host [TUNNEL-proxy-host [proxy-host [proxy-port]]]]`.
Defaults are `localhost` for the hosts and `localhost:3128` for the HTTP proxy.

Under valgrind:

```sh
libtool --mode=execute valgrind --leak-check=yes --error-limit=no \
        ./vortex-regression-client --disable-time-checks
```

### Caveats worth knowing

- **An unknown test name is not reported.** `--run-test=test_typo` matches nothing, runs
  no test at all and still finishes with `INFO: All test ok!`. When driving the suite from
  a script, check the `INFO: [end]` markers described below rather than the exit status.

  Note that checking whether the requested name *appears* in the output does not work
  either: the client echoes whatever it was given in its `INFO: running test=...` and
  `INFO: Checking to run test: ...` banner lines before matching anything.

- **Machine readable markers.** Every test is bracketed with markers keyed by the exact
  identifier `--run-test` accepts, and they are flushed so the `[begin]` marker survives a
  crash inside the test:

  ```text
  INFO: [begin] test_01
  Test 01: basic BEEP support [   OK   ] (finished in 0 secs, 2248 microseconds)
  INFO: [end] test_01
  ```

  A failing test emits `INFO: [failed] <name>` before exiting. These are the reliable
  signals for a script: `[end]` means the test ran and passed, and the human readable line
  between them is labelled with the display name (`Test 02-b`), not the identifier
  (`test_02b`), so it is not a good key to match on.
- **The poll/epoll re-run does not currently happen.** `main()` is written to re-run the
  whole suite once per available I/O mechanism, but `poll_tested` and `epoll_tested` are
  initialised to `axl_true`, so the `if (! poll_tested)` / `if (! epoll_tested)` guards
  never fire. In practice a full run only exercises `select(2)`. To cover poll/epoll the
  initialisers have to be flipped to `axl_false`.
- **Tests for optional modules self-skip.** When the library was built without TLS, SASL,
  XML-RPC, WebSocket, etc., the corresponding test prints a `--- WARNING:` line and returns
  success. A green run therefore does not by itself prove those areas were covered — check
  the output for warnings.
- `--run-test=` runs the selected tests and exits; the unfiltered path is a separate code
  block, so **three** places must be kept in sync when adding a test: the banner list, the
  `check_and_run_test()` block and the unfiltered `run_test()` block. The names printed in
  the banner are exactly the names accepted by `--run-test`, and both match the C function
  names (`test_04a`, `test_14h`, …).

## Listener contract

A full run needs the listener to be reachable on these ports:

| Port | Provided by | Used for |
|---|---|---|
| 44010 | `vortex_listener_new` | main listener, target of almost every test |
| 44011 | second `VortexCtx` | unified SASL API handling (SASL builds only) |
| 44012 | created on demand | fake listener started by the `create-listener` command (test 12) |
| 44110 | `vortex_listener_new` | endpoint used as the BEEP TUNNEL proxy (test 13) |
| 2443 | `vortex_listener_new` | plain BEEP target reached through the HTTP CONNECT proxy (test 16) |
| 44013 | noPoll listener | BEEP over WebSocket (test 17) |
| 44014 | noPoll TLS listener | BEEP over WebSocket with TLS (tests 18, 19) |
| 44015 | `vortex_listener_new` + `vortex_websocket_listener_port_sharing` | transparent port sharing: plain BEEP, WS and WS/TLS on one port (test 20) |
| 44016 | `vortex_listener_new6` on `::1` | IPv6 (tests 02a3, 02a4) |

Ports were deliberately moved off 443 to 2443 so the suite does not need root or a stopped
local HTTPS service.

### Running several suites at once

Every port above is a *base*: `--offset-port=NUM` adds `NUM` to all of them, up to 20000 so
that the highest (44110) stays inside the 16 bit range. Both programs take the option and
both must be given the same value.

```sh
./vortex-regression-listener --offset-port=1500          # binds 45510, 45511, 45610, 3943, ...
./vortex-regression-client   --offset-port=1500 --run-test=test_01
```

The HTTP proxy port is deliberately **not** shifted: it belongs to an external proxy server
rather than to the suite, so moving it would only break the connection to it.

This matters beyond convenience. Because the ports are fixed, a listener left behind by an
earlier run — or one a colleague is using in another terminal — will happily answer for the
one a script just started, which then dies on a bind error while every test runs against a
process nobody is tracking, with whatever build of the library it loaded when it started.
Giving each run its own offset makes that impossible rather than merely unlikely.

## Profiles

The behaviour the suite depends on is expressed as BEEP profiles registered by the
listener. A foreign listener has to implement these URIs — the set below *is* the scope a
compatible listener must cover. All are under
`http://iana.org/beep/transient/vortex-regression`.

| Profile URI suffix | Server-side behaviour required |
|---|---|
| *(base)* | echo profile: reply RPY with the same payload; also has an extended start handler |
| `/2` | extended start handler; used for default close-channel action checks |
| `/3` | reply out of order / wrong-order reply checks |
| `/4` | wrong-order reply checks |
| `/5` | ANS/NUL transfer of a selected file |
| `/6`, `/6bis` | additional reply-ordering profiles |
| `/zero` | transfer of zeroed binary frames |
| `/fake-listener` | accepts commands, notably `create-listener` (starts a listener on 44012) |
| `/block-tls` | connection on which TLS must be refused |
| `/fast-send` | content pushed from the `on connection accepted` handler |
| `/deny` | deliberately **not** registered by the listener: channel start must fail because the profile is unknown |
| `/deny_supported` | registered and therefore advertised in greetings, but its start handler always denies the channel |
| `/close-after-large-reply` | send a large reply and then close |
| `/mime` | MIME handling checks (headers, content type, transfer encoding) |
| `/ordered-delivery` | enforce ordered delivery at the server side |
| `/suddently-close` | close the connection abruptly while operating |
| `/mixing-replies` | mix ANS/NUL and RPY replies on the same channel |
| `/simple-ans-nul` | plain ANS…NUL reply sequence |
| `/ans-nul-wait` | ANS/NUL replies with a wait, for serialize checks |
| `/ans-nul-reply-close` | close driven from the `on connection accepted` handler after ANS/NUL |
| `/close-after-ans-nul-replies` | close right after finishing ANS/NUL replies |
| `/nothing` | registered with default handlers, does nothing |
| `/seqno-exceeded` | drive the channel close to the 4GB seqno wrap point |
| `/unified-sasl` | unified SASL API checks (on the 44011 context) |
| `/stats` | reports listener-side statistics |

## Using this suite to certify another implementation

Suggested order, from cheapest to hardest:

1. **Core session and channel semantics** — `test_01`, `test_02`, `test_03`, `test_09`,
   `test_10`, `test_11`. Greetings, channel start/close, MSG/RPY, window handling.
2. **Reply models** — the ANS/NUL family (`test_02k`, `test_02l`, `test_02l1`, `test_02m`,
   `test_04a`, `test_04ab`, `test_03b`, `test_03c`) and out-of-order replies (`test_11`).
3. **Numbering and limits** — `test_02n` (msgno reuse and wrap) and `test_02o1` (arithmetic
   at the 4GB seqno boundary). These are the classic sources of divergence between
   implementations, and the reason `test_02o1` exists: the area went uncovered for a long
   time because `test_02o`, the test that was meant to cover it, is disabled.
4. **MIME** — `test_01d`, plus `test_02l1` for the MIME-disabled NUL case.
5. **Robustness** — `test_01g1`, `test_01h`, `test_01w`, `test_01x`, `test_02a2`,
   `test_02j`. Malformed headers, floods, oversized frames, abrupt disconnects.
6. **Profiles on top** — TLS (`test_05*`), SASL (`test_06*`), TUNNEL (`test_13`),
   ALIVE (`test_15*`), XML-RPC (`test_07`), WebSocket (`test_17`–`test_20`).

The `test_00*` group is LibVortex-internal plumbing and can be ignored. `test_14*` (PULL)
and `test_21`/`test_22` (external transport) describe LibVortex API shapes rather than wire
behaviour; they are only relevant if the new implementation offers equivalent facilities.
